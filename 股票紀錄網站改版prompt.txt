這是我已經複製好的一份股票紀錄系統專案。

這次目標不是做正式後端版，而是把這份專案改造成「純前端 local-first 版」。

請你先不要直接大幅重構。請先完成技術可行性調查，再提出修改計畫，最後才開始修改。

最終目標：

1. 專案可以部署到 GitHub Pages。
2. 不需要 Python 後端。
3. 不需要 PostgreSQL。
4. 不需要任何 server runtime。
5. 使用者資料全部存在瀏覽器 IndexedDB。
6. 前端盡量自動抓取股市資料。
7. 如果股市資料無法自動抓取，必須提供手動補價格功能。
8. 系統要保留原本股票分析練習的核心商業邏輯。
9. 最後必須 npm run build 成功，並可作為靜態網站部署。

請分成以下階段處理。

========================================
第一階段：閱讀與盤點現有專案
========================================

請先完整閱讀目前專案結構，找出：

1. 目前前端框架與 build tool。
2. 是否使用 Vite。
3. 是否有 React Router 或其他前端 routing。
4. 目前資料來源在哪裡。
5. 目前是否呼叫後端 API。
6. 目前是否依賴 Python server。
7. 目前是否依賴 PostgreSQL。
8. 目前是否依賴 .env 的 DATABASE_URL。
9. 目前哪些功能可以保留。
10. 目前哪些功能需要改成純前端。

請先輸出一份專案盤點報告，不要直接修改。

========================================
第二階段：股市資料 API 可行性調查
========================================

請調查並實測可用於純前端的台股資料來源。

優先調查：

1. TWSE OpenAPI
2. FinMind API
3. 其他可由瀏覽器直接 fetch 的公開台股資料來源

請注意：

1. 必須確認資料來源是否允許瀏覽器直接 fetch。
2. 必須確認是否有 CORS 問題。
3. 必須確認是否需要 API key。
4. 如果需要 API key，必須判斷該 key 是否可以公開。
5. 不可把任何需要保密的 token、API key、secret 寫到前端。
6. 如果是 Vite 專案，VITE_ 環境變數視為公開資訊，不可放秘密。
7. 不可依賴 Python 後端代理 API。
8. 不可依賴 PostgreSQL。
9. 不可依賴 server-side scheduler。

請建立一份資料來源評估表，至少包含：

- provider 名稱
- 可取得的資料類型
- 是否支援股票代號查詢
- 是否支援歷史日收盤資料
- 是否支援當日價格
- 是否支援成交量
- 是否需要 token
- token 是否可公開
- 是否通過瀏覽器 CORS 測試
- rate limit
- 適合用途
- 失敗風險
- 最終建議是否採用

請實際寫一個小型測試程式或暫時測試函式，從瀏覽器環境測試 fetch 是否能成功，不要只用 curl 或 Node.js 測試，因為 Node.js 不會遇到瀏覽器 CORS 限制。

========================================
第三階段：決定前端資料抓取策略
========================================

請根據第二階段調查結果，設計一個可替換的股票資料 provider 架構。

目標是讓系統未來可以替換資料來源。

請設計至少以下 provider：

1. TWSEProvider
2. FinMindProvider，僅在不需要秘密 token 或可安全使用時啟用
3. ManualPriceProvider
4. MockProvider，用於本機測試或資料源故障時

資料抓取策略：

1. 使用者新增股票分析時，系統嘗試自動抓取分析當天價格。
2. 使用者開啟網站時，系統自動檢查需要更新的股票。
3. 使用者開啟網站時，系統自動檢查哪些紀錄已滿一週。
4. 已滿一週但尚未檢視的紀錄，系統嘗試抓取一週後價格。
5. 使用者可以手動點擊「更新價格」。
6. 如果 API 失敗，系統不能刪除紀錄。
7. 如果 API 失敗，標記 data_error，並顯示錯誤原因。
8. 如果 API 失敗，使用者可以手動補價格。
9. 如果一週後遇到非交易日，使用下一個可取得交易日價格，並保存實際使用的價格日期。

請注意：純前端靜態網站無法保證在使用者沒有開啟網頁時自動執行。  
所以自動更新邏輯應該是「開啟網站時自動檢查」與「手動點擊更新」，不是 server background job。

========================================
第四階段：IndexedDB 資料層
========================================

請把資料儲存改成 IndexedDB。

需求：

1. 所有股票分析資料存在 IndexedDB。
2. 不使用 PostgreSQL。
3. 不使用後端 API 儲存資料。
4. 不使用 localStorage 儲存主要資料。
5. IndexedDB 需要有 schema version。
6. 未來 schema 改版時要能 migration。
7. 需要提供 export JSON。
8. 需要提供 import JSON。
9. 匯入時要驗證資料格式。
10. 匯入時要避免重複資料。
11. 匯入失敗要顯示清楚錯誤。
12. 使用者可以清除本機資料，但要有確認提示。

資料至少需要保存：

- analysis id
- stock symbol
- stock name
- analysis date
- direction，預設 bullish
- note
- tags
- analysis price
- analysis price date
- analysis snapshot
- review due date
- one week review price
- one week review price date
- one week return percentage
- success status
- latest price
- latest price date
- latest return percentage
- status
- data source
- fetch status
- error message
- created at
- updated at

狀態至少包含：

- pending
- ready_to_review
- reviewed
- tracking
- data_error

========================================
第五階段：保留商業邏輯
========================================

請保留以下核心商業邏輯：

1. 使用者每天最多新增三支股票。
2. 同一天同一支股票不可重複新增。
3. 不同日期可以重複分析同一支股票。
4. 分析方向預設為看多。
5. 分析當天價格一旦保存，不可被最新價格覆蓋。
6. 一週後價格一旦保存，不可被後續價格覆蓋。
7. 最新價格可以持續更新。
8. 統計勝率只計算已完成一週檢視的紀錄。
9. 尚未滿一週的紀錄不可納入正式一週勝率。
10. 報酬率計算必須基於保存的歷史價格，不可每次用最新價格重算歷史結果。
11. 看多成功條件：一週後價格 > 分析當天價格。
12. 看空成功條件：一週後價格 < 分析當天價格。
13. 價格相同時標記為 flat 或 failed，但畫面要清楚顯示。
14. 資料抓取失敗時，不可刪除紀錄。
15. 使用者可以手動修正價格資料，但必須保留修正時間與來源。

報酬率計算：

returnPercentage = (comparisonPrice - analysisPrice) / analysisPrice * 100

需要區分：

- 一週報酬率
- 目前浮動報酬率
- 後續累積報酬率
